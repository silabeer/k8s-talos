# Внешний центр сертификации для mTLS

Как подключить mTLS меша к PKI, которую ведёт служба информационной
безопасности: оффлайн-корень, промежуточные под её контролем, выпуск через
OpenBao. Документ описывает две схемы и то, что нужно поменять в репозитории.
Ни одна из них сейчас не реализована: работает вариант с корнем, который
генерирует `bootstrap/mesh.sh`.

## Что происходит сегодня

`bootstrap/mesh.sh` создаёт корневой центр сертификации, подписывает им по
промежуточному на каждый кластер и кладёт материал в секрет `cacerts` в
неймспейсе `istio-system`. Лифы выписывает istiod. Ключи лежат в
`infra/out/istio-ca/` и в git не попадают.

Проверить цепочку на живом кластере:

```bash
zt=$(kubectl -n istio-system get pods -l app=ztunnel -o jsonpath='{.items[0].spec.nodeName}')
istioctl ztunnel-config certificate --node "$zt"
```

Вывод показывает три уровня: leaf на сутки, промежуточный, корень.

## Почему лифы нельзя выдать заранее

Лиф выписывается на каждую рабочую нагрузку отдельно, живёт по умолчанию
сутки и обязан нести URI SAN вида
`spiffe://<домен доверия>/ns/<namespace>/sa/<serviceaccount>`. Их столько же,
сколько подов, и они перевыпускаются постоянно. Поэтому интеграция с внешней
PKI — это всегда подключение центра, который подписывает, а не передача
готовых сертификатов.

В ambient за сертификатом ходит не сам под, а ztunnel узла: он
аутентифицируется своей учётной записью и запрашивает сертификат для той
нагрузки, которую представляет. Это важно для схемы Б.

## Схема А: промежуточный от ИБ лежит в кластере

Самая простая. Служба ИБ выпускает промежуточный сертификат на каждый кластер
от своего оффлайн-корня и передаёт вам его вместе с ключом. Лифы по-прежнему
выписывает istiod.

Что положить перед запуском `make mesh`:

```
infra/out/istio-ca/
  root-cert.pem            корень от ИБ, только публичная часть
  east/
    root-cert.pem          тот же корень
    ca-cert.pem            промежуточный этого кластера
    ca-key.pem             его приватный ключ
    cert-chain.pem         промежуточный + корень, именно в таком порядке
  west/
    ...
```

`mesh.sh` генерирует материал только если файлов нет, поэтому принесённый
будет использован как есть.

Плюс: ничего дополнительно разворачивать не нужно. Минус: приватный ключ
промежуточного лежит в кластере, в секрете `cacerts`.

## Схема Б: промежуточный остаётся в OpenBao

Каждый лиф подписывает OpenBao, ключ промежуточного из него не выходит.
Собирается из трёх частей:

1. **OpenBao**, движок PKI, промежуточный подписан оффлайн-корнем ИБ.
   Роль выпуска должна разрешать URI SAN формата SPIFFE и не требовать
   привязки к доменным именам.
2. **cert-manager** с `Issuer` типа Vault, направленным на этот движок.
   Аутентификация в OpenBao — Kubernetes auth или AppRole.
3. **istio-csr**, который выставляет gRPC-интерфейс центра сертификации
   Istio и превращает запросы меша в объекты `CertificateRequest`
   cert-manager.

istiod и ztunnel направляются на istio-csr переменной `CA_ADDRESS`. Секрет
`cacerts` при этой схеме не используется вовсе: корень распространяется через
configmap `istio-ca-root-cert`, которую поддерживает istio-csr.

Обязательная для ambient деталь:

```
--ca-trusted-node-accounts=istio-system/ztunnel
```

Без этого флага istio-csr отклоняет запросы: ztunnel просит сертификат не для
себя, а для представляемой нагрузки. Поддержка ambient есть начиная с версий
istio-csr, где появился этот флаг; на момент написания актуальна 0.17.0.

Плюс: приватный ключ промежуточного недоступен из кластера, вся политика
выпуска и аудит живут в OpenBao. Минус: три дополнительных компонента, и меш
перестаёт выпускать сертификаты, если недоступен OpenBao или cert-manager.

## Требования к промежуточному сертификату

Передать службе ИБ вместе с запросом:

- `basicConstraints: CA:TRUE`, разумно `pathlen:0`;
- `keyUsage` с `keyCertSign` и `cRLSign`;
- для схемы А обязателен URI SAN
  `spiffe://cluster.local/ns/istio-system/sa/istio-pilot-service-account`,
  иначе istiod не примет материал;
- домен доверия одинаковый во всех кластерах меша, у нас `cluster.local`;
- по одному промежуточному на кластер, а не общий на все: компрометация
  одного не тянет за собой остальные;
- в `cert-chain.pem` цепочка промежуточный плюс корень, в `root-cert.pem`
  только корень.

Сроки, от которых можно отталкиваться: лиф сутки, промежуточный от года до
пяти, корень десять лет и оффлайн.

## Чего в репозитории не хватает

Для схемы А:

- явная проверка принесённого материала в `mesh.sh`: что это CA, что есть
  нужный URI SAN, что цепочка собрана в правильном порядке. Сейчас ошибка
  вылезет не сразу, а отказом рукопожатия;
- перевыпуск промежуточного без пересоздания меша.

Для схемы Б:

- приложение cert-manager уже есть в `east`, нужно добавить в `west`;
- новое приложение `istio-csr` и `Issuer` на OpenBao;
- в values Istio выключить `cacerts` и указать `CA_ADDRESS`;
- в `mesh.sh` убрать создание корня, оставив только обмен доступом к
  API-серверам.

## Что использовать не получится

Отдать выпуск лифов внешнему серверу SPIRE в ambient нельзя. ztunnel получает
сертификаты по gRPC-интерфейсу центра сертификации Istio
(`IstioCertificateServiceClient`, адрес в `CA_ADDRESS`) и сокет SPIFFE
Workload API не читает. Официальная интеграция Istio со SPIRE построена именно
на этом сокете и описана только для sidecar и шлюзов.

Если общий корень доверия со SPIRE всё же нужен, работающий вариант — сделать
SPIRE вышестоящим центром, который подписывает промежуточный для istiod. Лифы
при этом по-прежнему выписывает istiod.
